Help / Concepts

Reticulum uses interfaces—the different ways a node communicates over a LAN, radio, or reachable TCP link.

TCP Server vs TCP Client

TCP Client                    TCP Server
This node → Remote server     Remote node → This node

A TCP Client initiates an outbound connection to a remote Reticulum TCP Server. A TCP Server waits on this machine for inbound connections.

What do I need before creating a TCP Client?

  • Remote hostname or IP address
  • Remote TCP Listen Port
  • Matching IFAC network name and passphrase if the remote server uses IFAC
  • Confirmation from that operator that the server is reachable and accepting connections

Example: remote server listen_ip = 100.64.10.20, listen_port = 4242; this node uses target_host = 100.64.10.20, target_port = 4242.

If IFAC values do not match, a TCP connection may exist but Reticulum traffic will not work correctly. If the Target Port does not match the remote Listen Port, the TCP connection will fail. If the remote server is unreachable, the interface remains disconnected.

What do I need before creating a TCP Server?

Choose a local Listen IP (where this machine waits) and Listen Port (the local room number for that service). The client must be able to reach that address, and both ends must use matching IFAC when configured.

Creating a TCP Server does not open a router, firewall, or Tailscale. A single IP can host multiple TCP Server interfaces as long as the ports differ:

Public User TCP      0.0.0.0:4242
Trusted Backbone     0.0.0.0:4243
Testing              0.0.0.0:4244

When do I need Transport Mode?

Leave Transport Mode Off when this machine alone needs the TCP Client connection. Enable it only when this node should route Reticulum traffic for other nodes. In that case, it also needs another usable interface—such as TCP Server, AutoInterface, or RNode—for those other nodes to reach it.

VM → TCP Client → Your Pi → TCP Client → Remote RNS Server

For the VM to reach the remote network through the Pi, the Pi needs Transport Mode and both a local-side and remote-side interface.

Using Tailscale with Reticulum

Tailscale is usually easier and safer than public router forwarding for private, trusted Reticulum TCP links. Install it on both machines, join them to the same tailnet, ensure policies allow the connection, then use the server’s Tailscale IP or MagicDNS name.

Server: listen_ip = server's Tailscale IP; listen_port = 4243
Client: target_host = server's Tailscale IP or MagicDNS name; target_port = 4243

The Reticulum Admin GUI can also be reached over Tailscale for private administration, without exposing its web portal publicly. This project does not install or configure Tailscale for you.

AutoInterface

Discovers nearby Reticulum nodes on the same local network. It needs compatible local networking and IPv6/link-local availability where required; no remote server address is needed. Managed Linux rnsd runs with host networking so it can see the server's real LAN interfaces, but host networking alone does not guarantee AutoInterface connectivity.

IFAC

Shared access protection for one interface, similar to a shared Wi-Fi password. It does not automatically carry over from another interface. Use the interface default size unless the other operator requires a custom value.

Local IP vs public IP

listen_ip is an address assigned to this server, not normally its public Internet address. In the managed native-Linux installation, rnsd uses host networking: 0.0.0.0 is all host IPv4 interfaces, 192.168.1.85 is a LAN address only, and 100.x.x.x is a Tailscale address only when assigned to the host. A remote client uses a reachable address that routes to the server.
